# Demand-based parallel GPU processing

The primary Unreal world uses `-nullrhi`. GPU render workers are independent replicas using the existing UE5 hardware ray-query extension for LiDAR/radar and normal GPU camera captures. Camera-only workers disable the dedicated external-ray viewport and ray-query forcing. The UE5 renderer does not force the external ray pass for camera/reflection captures; cameras keep their own lighting flags. A sensor stream belongs to one worker; individual rays/pixels are parallel on that GPU. Different streams can use different GPUs. A single camera or LiDAR stream is not split across several GPUs.

Automatic startup launches only the primary. Applying a GPU sensor loadout starts the required renderers while paused, replicates the current world to late joiners, and proves synchronized sensor frames before returning. Removing all GPU sensors releases every renderer; IMU/GNSS remain on the primary. Worker count changes recreate sensor streams and thus change sensor actor IDs. Vehicle actor IDs stay unchanged. Scaling is prohibited during recording, live running and native replay. World warmup advances simulation time.

`gpu_resources.py` estimates initial demand from camera pixel count and LiDAR/radar point rates. These costs are scheduling heuristics, not GPU timings. The native CARLA router assigns new subscriptions to the least estimated load and releases reservations when sensors are destroyed. IMU/GNSS no longer occupy GPU routing slots. Late-joining workers resolve primary actor IDs to their own local sensor streams; they do not assume stream counters match. A condition variable waits for the spawn snapshot to be applied before issuing the streaming token. Native ROS controls for an assigned stream also use its worker-local ID. The rebuilt Python client keys subscriptions by endpoint plus stream ID, stores the actual returned token for unsubscribe, and serializes socket shutdown on the Asio strand. These changes address collisions between worker-local stream IDs and a close/reconnect race found during live scaling tests. All active workers receive scene updates and keep independent scene copies; this change does not implement shared cross-process scene memory.

Runtime > Measure best GPU count compares one through the number of GPU streams, capped at four. Each candidate has 10 warmup and 50 measured synchronized frames. All sensor frame IDs and timestamps must match. The selected count is the fewest workers within 10% of the lowest mean complete-frame time. Measurements are keyed by sensor configuration, map, weather and actor models. Motion and traffic state can still change during a benchmark; results are workload samples, not universal performance guarantees. Reprofile after substantial scenario changes. It is never permissible to change fidelity or skip samples to make a profile look faster.

The timing panel separates controls/signals, world tick, additional sensor wait, state refresh, ROS/recording, and preview encoding. World tick time includes physics, other actor work, Traffic Manager, replication and RPC; it is not a pure physics measurement. Sensor arrival timing is time from world-tick request to delivery, not CUDA kernel duration. The regular run loop remains capped at 20 simulation steps per wall-clock second when able. Profiling measures uncapped stepping.

## Physics decision

The installed Chaos vehicle implementation uses `PhysicsParallelFor` in `ChaosVehicleManagerAsyncCallback.cpp`; the rigid solver uses CPU task-graph jobs in `PBDRigidsSolver.cpp` and particle parallel loops in `PBDRigidsEvolutionGBF.cpp`. These paths do not expose an interchangeable GPU rigid-body/vehicle solver. Worker replay already disables vehicle physics on replicas (`CarlaReplayerHelper.cpp`). GPU particle effects or GPU ray queries are not replacements for full vehicle dynamics.

Vehicle/rigid-body physics remains on the CPU with the existing fixed step, substeps, collision and determinism settings. No GPU-physics speedup is claimed. Replacing Chaos would require a separate solver integration, complete vehicle/tire/suspension and collision parity tests, and repeatability/replay tests. The sensor changes do not require that replacement.

Native changes include UE5 `Renderer/Private/DeferredShadingRenderer.cpp` and CARLA `Sensor/GpuSensorDispatcher.cpp`, plus LibCarla streaming/client code and LibCarla `multigpu/router.{h,cpp}`, `primaryCommands.{h,cpp}`, CARLA `Server/CarlaServer.cpp`, `Game/CarlaEngine.{h,cpp}`, and `Sensor/Sensor.cpp`. Launcher: `/mnt/simulations/carla/carlab/host-setup/scripts/carla-multigpu.py`. Controller and UI: `gpu_resources.py`, `controller.py`, `static/gpu-resources.js`, `static/app.js`, `static/index.html`.
